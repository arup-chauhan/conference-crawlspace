# Deliverables

Choose a structure that fits the audience and goal. Output formats depend on the host's tools.

## Reports

For explanatory reports, teach the ideas found in the sources. Cover the problem, simple model, mechanism, reported outcome, limits, and connections.

Include substantive talk summaries and source locations. For decision reports, add comparisons and practical implications. Put proposed experiments in a separate section when useful.

Match the detail to the request. Full transcripts and reproduced slides are not default outputs.

For Word or PDF, follow the relevant skill's rendering and verification workflow. If those tools are unavailable, provide useful Markdown with source links. Explain any requested-format limitation.

Cite substantive claims nearby. Include a source index.

## Benchmark plans

For each experiment, include:

- Hypothesis, baseline, and workload.
- Configuration differences and fixed conditions.
- Procedure and measurement definitions.
- Acceptance criteria or a decision rule.
- Limitations.

Use the user's targets when available. Do not invent measured outcomes or approved numeric thresholds.

A comparison table can vary controller type, traffic, data skew, cache state, or resource pressure. Avoid changing everything together when that would hide the cause.

Keep service, batch, storage, and inference tests distinct where their controls differ.

## Presentations and animation

First check for live presentation sessions or supported authoring tools. Follow the available presentation skill.

For a learning deck, explain the problem, mechanism, source example, tradeoff, and connections. Use illustrations to teach the mechanism.

For a decision deck, add architecture options and implications. Center experiments only when the user requested benchmark planning.

Explain the talks themselves. A list of research leads or future tests does not replace their content.

Put detailed sources in notes or an accessible references view. Show evidence limits when they affect a slide's meaning.

Check what the output format actually supports before promising animation. Use reveals to explain steps, comparisons, or clearly labeled example workloads.

Keep content readable and navigation usable. Transitions are not object animations. A static PDF cannot provide PowerPoint animation.

If native animation is unavailable, consider a self-contained browser deck. Use this fallback only when the user has not required another format. Explain the format and include:

- Keyboard and button navigation.
- A pause control for autoplay.
- Reduced-motion behavior.
- An accessible sources and notes view.

Avoid external runtime dependencies when offline sharing matters. Inspect every slide at the intended viewport. Make sources and illustrative assumptions easy to check.

If a required format is unsupported, explain the exact limit. Preserve useful work and offer the closest available output. Do not silently substitute an incompatible file.

## Delivery checks

Confirm the event, scope, evidence coverage, source links, file readability, and accessible paths.

For decks, inspect every slide. Test navigation and animation in a supported viewer.

Compare the output with the source briefs and topic inventory. Explain substantive mechanisms and represent the key talks. Keep gaps visible rather than filling them with guesses.

For archives, check that the final files are included. Exclude task-private data, caches, credentials, and personal filesystem paths.

Keep validation records out of audience-facing content. Report remaining gaps and only the checks or reproduction work actually completed.
